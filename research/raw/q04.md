# q04 — Tauri 2 / WebView2 데스크톱 앱 테스트·검증 하네스 모범사례

- 조사일: 2026-11-18
- 대상 프로젝트: 구석메모 (Tauri 2 + WebView2, 현재 `--selftest` 플래그 + plan_setup/cdp-*.cjs CDP 스크립트 + 수동 debug exe)
- 목적: E2E 도구 지형, Rust 테스트 패턴, GUI-less CI 검증, 품질 게이트 구성, store.json 마이그레이션 회귀 테스트 정리

---

## 핵심 요약

1. **공식 권장 E2E 경로는 "WebDriver 계열" 하나로 수렴**했다. 2025~2026년 사이 WebdriverIO 진영의 `@wdio/tauri-service`가 사실상 표준이 되었고, Tauri 공식 문서도 이를 "recommended way"로 명시한다. `embedded` 드라이버(플러그인 기반, macOS까지 지원)와 `external` 드라이버(`tauri-driver`, Win/Linux) 두 경로가 있다.
2. **현재 구석메모의 CDP 스크립트 방식은 공식 지원 경로와 같다.** Playwright 공식 문서가 WebView2 앱 자동화를 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port` + `connectOverCDP`로 문서화했으므로, cdp-*.cjs를 유지하되 Playwright test runner로 옮기면 fixture(포트 분리, user-data-dir 격리, 프로세스 정리)를 공짜로 얻는다.
3. **GitHub-hosted Windows runner에서 실제 Tauri 창을 띄우는 테스트가 동작한다**(공식 CI 문서 + 실제 워크플로 증거). 단 GUI 상호작용(UIA/실입력)은 불안정할 수 있고, WebView2 런타임은 이미지가 관리해주지 않아 버전 불일치 이슈가 실재한다. 셀프테스트(플래그로 띄워 로그/종료코드 검증)는 CI에서도 유효한 패턴이며 실제 사례가 있다.
4. **Rust 단위 테스트는 `tauri` 크레이트의 `test` feature + `tauri::test` MockRuntime**이 공식 수단이지만 unstable이다. 커맨드 로직을 순수 함수로 분리해 테스트하는 것이 더 견고하다.
5. **`tauri::generate_context!()`는 컴파일 타임에 frontendDist(dist/) 존재를 요구**하므로, CI에서 `cargo clippy/test` 전에 `npm run build`를 먼저 돌려야 한다. 이게 품질 게이트 순서의 핵심 제약이다.
6. **store.json 마이그레이션은 플러그인 내장 프레임워크가 없다.** `__version` 키 + 로드 시 코드 마이그레이션이 사실상 표준이며, 회귀 테스트는 "마이그레이션 순수 함수 + fixture JSON 단위 테스트"와 "구버전 store.json을 app-data에 심고 selftest로 검증" 두 층이 실용적이다.

## 상세 메모

### A. E2E 테스트 도구 지형

**A-1. 공식 권장: `@wdio/tauri-service`(WebdriverIO)**
- Tauri 공식 문서는 "recommended way to use [WebDriver] with Tauri is WebdriverIO and the `@wdio/tauri-service`"라고 명시. Windows/Linux/macOS 지원.
- 세 가지 driver provider:
  - `embedded`(기본): 앱 안에 WebDriver 서버를 띄우는 `tauri-plugin-wdio-webdriver` 플러그인 방식. 외부 드라이버 불필요, macOS도 지원.
  - `external`: 별도 `tauri-driver` 프로세스. Windows/Linux만. Windows에서는 Edge WebDriver 버전 동기화가 필요(서비스가 자동 관리).
  - `crabnebula`: CrabNebula 포크. 크로스플랫폼이나 macOS는 유료 API 키 필요.
- 부가 가치: `browser.tauri.execute()`로 Rust 커맨드 직접 호출, `browser.tauri.mock()`으로 invoke 모킹, 프론트/백엔드 로그 캡처, multiremote, 워커별 드라이버 스폰.
- **브라우저 모드**: 바이너리/드라이버/플러그인 없이 Vite dev server + 일반 Chrome에서 프론트만 테스트. `invoke()` 인터셉트로 커맨드 모킹·인자 단언. GUI 없는 CI에 가장 가벼운 진입점.
- 유지보수: `webdriverio/desktop-mobile` monorepo(별 22, MIT, 907+ 커밋, 활발). npm `@wdio/tauri-service` 1.5.1, 주간 다운로드 ~8만(2026-10 기준). 생태계가 작지만 WebdriverIO 조직이 관리.

**A-2. `tauri-driver` 직접 구동(Selenium/자체 하네스)**
- `cargo install tauri-driver --locked`. WebDriver Intermediary Node로, 네이티브 드라이버(Windows: msedgedriver, Linux: WebKitWebDriver)를 감싼다. 포트 2개(`--port` 4444, `--native-port` 4445).
- README는 여전히 "(pre-alpha)" 표기 — API 안정성 주의. 다만 crates.io 릴리스는 2026년에도 활발(2.1.0, 2026-09; 3.0.0-alpha.1도 존재).
- Windows에서 msedgedriver와 Edge/WebView2 버전 불일치 시 "테스트 스위트가 연결 단계에서 hang"한다고 공식 문서가 경고. `msedgedriver-tool`(`cargo install --git https://github.com/chippers/msedgedriver-tool`)로 설치된 런타임에 맞는 드라이버를 다운로드. `@wdio/tauri-service`는 이를 `autoDownloadEdgeDriver`로 자동화(기본 on).
- macOS는 WKWebView 드라이버가 없어 직접 구동 미지원(embedded 경로 또는 Appium).

**A-3. CDP 직접 방식(현재 구석메모 방식의 공식 근거)**
- Playwright 공식 문서: WebView2는 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=NNNN`(또는 `EnsureCoreWebView2Async` 인자)로 CDP를 열고 `chromium.connectOverCDP('http://localhost:NNNN')`로 자동화.
- 병렬/반복 테스트 시 `WEBVIEW2_USER_DATA_FOLDER`를 테스트마다 다르게 — 같은 user-data-dir를 공유하면 간섭.
- 공식 예시는 child_process로 exe spawn → stdout "WebView2 initialized" 대기 → connectOverCDP → taskkill 정리. 현재 cdp-*.cjs 수작업과 동일 구조이므로 **Playwright test fixture로 포팅하면 포트/격리/정리를 표준화**할 수 있다.
- Tauri에서도 동일하게 동작: Tauri 앱 프로세스에 env var를 주고 띄우면 WebView2가 CDP 포트를 연다.

**A-4. WinAppDriver / 대안**
- Microsoft의 WinAppDriver는 수년간 미유지보수, 마지막 안정 릴리스 v1.2.1(구식), JSONWP만 지원 → 최신 Appium과 비호환. Appium 측 windows driver도 deprecated로 표시하고 WinCore Driver(신규) 또는 NovaWindows Driver(서드파티)를 대안으로 안내.
- WebdriverIO 문서도 "현재 Windows 앱 자동화에 안정적인 드라이버가 없다"고 명시.
- 결론: **WebView2 기반 Tauri 앱에 WinAppDriver는 무의미** — 렌더링 DOM에 접근 못 하고 UIA 수준만 가능. CDP 또는 WebDriver(Edge)가 정답.

### B. Rust 단위/통합 테스트 패턴

**B-1. `tauri::test` (공식, unstable)**
- `tauri` 크레이트 `test` feature로 활성화. 일반적으로 `[dev-dependencies] tauri = { version = "2", features = ["test"] }`.
- `mock_builder()` → `Builder<MockRuntime>` 생성 → `mock_context(noop_assets())` 또는 `generate_context!("test/fixture/src-tauri/tauri.conf.json")`로 빌드 → `WebviewWindowBuilder`로 가짜 웹뷰 생성 → `get_ipc_response`/`assert_ipc_response`로 `invoke`를 시뮬레이션(INVOKE_KEY 필요).
- 네이티브 웹뷰 라이브러리는 실행되지 않는다(공식 문서 명시). 즉 **IPC 라우팅/커맨드 로직은 테스트 가능, 렌더링은 불가**.
- **한계**: unstable로 명시(API 변경 가능); `generate_context!`는 여전히 유효한 tauri.conf.json 필요(fixture 경로로 우회 가능); State/AppHandle 의존 커맨드는 mock 앱에서 `app.state::<T>()`로 꺼내 직접 호출하는 패턴 사용.

**B-2. 더 견고한 패턴: 커맨드 = 얇은 래퍼, 로직 = 순수 함수**
- 커뮤니티 문서(agents-inc skills 예시 포함)에서도 "injected parameter 없는 커맨드는 함수 직접 호출로 단위 테스트"를 제시. MockRuntime 없이 `fn greet(name)->String` 형태 로직을 `#[cfg(test)]`로 테스트하면 웹뷰·컨텍스트 의존이 없다.
- 구석메모의 Rust 로직(메모 저장/로드, store 마이그레이션, 파일 IO)은 **AppHandle을 받지 않는 순수 함수 + 커맨드가 위임** 구조로 두면 `cargo test`만으로 커버 가능 — CI에서 가장 빠르고 안정적인 층.

**B-3. 프론트엔드 mock(커맨드 계약 테스트)**
- `@tauri-apps/api/mocks`: `mockIPC(handler)`로 `invoke` 인터셉트, `mockWindows('main','second')`로 창 존재 모킹, `clearMocks()` 필수(테스트 간 상태 오염 방지).
- 이벤트 모킹은 api 2.7.0부터 `mockIPC(..., { shouldMockEvents: true })`로 `emit`/`listen` 부분 지원. `emitTo`/`emit_filter` 미지원.
- vitest + jsdom 조합이 공식 예시(WebCrypto 없어서 `getRandomValues` 폴리필 필요하다는 주석도 있음).
- 용도: 프론트가 올바른 커맨드명·인자로 invoke하는지, 백엔드 응답 분기가 맞는지 검증 — "커맨드 계약" 회귀 방지.

### C. GitHub Actions에서 GUI 없이/있이 검증

**C-1. 공식 CI 예시가 보여주는 사실**
- 공식 문서의 GitHub Actions 예시는 **Windows(`windows-latest`)에서 실제 앱을 띄우는 WebDriver 테스트를 그대로(`yarn test`) 실행**한다. 즉 hosted Windows runner에서 Tauri 창 생성 + WebDriver 연결은 동작한다.
- Linux는 `xvfb` + `webkit2gtk-driver`로 가짜 디스플레이. Windows는 별도 가짜 디스플레이 불필요.
- 워크플로는 `cargo test`를 WebDriver 테스트 **전에** 두는데, 주석이 "깨진 앱을 테스트하지 않기 위해" — 품질 게이트 순서의 근거.

**C-2. Hosted runner의 세션 특성 (뉘앙스)**
- GitHub-hosted Windows runner는 백그라운드 서비스로 동작해 "완전한 인터랙티브 데스크톱 세션은 아니다"는 보고가 있다(FlaUI 기준 일부 테스트 불안정). 그러나 **창 생성·렌더링·CDP 연결·스크린샷 수준은 동작**한다 — Tauri 공식 CI 문서, mimi의 hosted `windows-11-arm` 스모크 런치, WGC 스크린샷 도구 사례들이 증거.
- 실무적 결론: **DOM/CDP 수준 검증 + 창 뜨는지 확인 + 셀프테스트는 hosted runner에서 OK**. 실마우스/키보드·UIA·트레이 아이콘 상호작용 같은 네이티브 상호작용 검증은 self-hosted(인터랙티브 로그온)로 미루는 게 안전.
- self-hosted runner를 **Windows 서비스로 설치하면 세션0이라 GUI 불가** — autologon/콘솔 세션 필요(FlaUI 가이드·SEP 블로그 공통 지적). 구석메모에 self-hosted를 쓴다면 반드시 인터랙티브 모드로.

**C-3. WebView2 런타임 주의**
- `actions/runner-images`는 WebView2를 별도 설치/관리하지 않는다고 공식 답변 — 베이스 이미지에 딸려오며 Edge와 버전이 어긋난 사례 보고(#9538). Tauri 앱이 WebView2 evergreen을 요구하므로 CI에서 `MicrosoftEdgeWebview2Setup.exe`(evergreen bootstrapper, `go.microsoft.com/fwlink/p/?LinkId=2124703`, `/silent /install`)로 최신 런타임 보장 단계를 넣는 게 안전. StateUI 워크플로가 동일 패턴 사용(검색 결과 경유).
- `msedgedriver` 자동 동기화는 `@wdio/tauri-service`의 `autoDownloadEdgeDriver`(기본 on) 또는 `msedgedriver-tool`이 처리 — 드라이버 버전을 하드코딩하면 windows-latest 이미지 업데이트로 깨진다(pan-agent 워크플로 주석, 검색 결과 경유).

**C-4. "셀프테스트 패턴"의 실효성**
- 플래그/환경변수로 앱을 띄워 내부 자가검증 후 로그+종료코드로 판정하는 방식은 실제 사례가 있다: mimi가 `windows-ci-smoke.ps1`로 release exe를 hosted ARM runner에서 띄워 overlay 컨트롤을 invoke하고 건축/아키를 검증. 즉 **"실제 바이너리를 CI에서 띄우는 스모크"는 hosted Windows에서 동작**.
- 구석메모의 `--selftest`(26개 테스트 → `%TEMP%\guseok-qa.log`)는 이 패턴에 정확히 해당. CI 이식 시 고려점:
  - WebView2 창이 떠야 하므로 hosted Windows에서 OK(위 C-2 범위 내).
  - 로그 파일을 artifact로 업로드, 실패 시 종료코드≠0.
  - 트레이/단일인스턴스/자동시작 같은 OS 통합 기능은 hosted runner의 제한된 세션에서 오탐 가능 → selftest에 "CI 모드" 스위치로 해당 항목 skip/느슨 검증 권장.

**C-5. 가장 가벼운 CI 경로 — 브라우저 모드**
- `@wdio/tauri-service`의 browser mode는 바이너리·드라이버 없이 Vite dev server + Chrome에서 프론트 테스트. "GUI 없이"라는 요구에 가장 근접한 공식 경로. invoke 모킹으로 커맨드 계약까지 검증 가능.

### D. 품질 게이트 구성 사례

실제 Tauri 프로젝트 CI에서 관찰된 표준 레이어(발췌 근거: mimi, sealed-env-studio, noderium, TurboFiles, ecky 워크플로 — mimi와 sealed-env-studio는 실제 fetch):

1. **순서 제약의 핵심**: `tauri::generate_context!()`가 컴파일 타임에 `frontendDist`를 평가 → `cargo clippy`/`cargo test`/`cargo build` 전에 `npm ci && npm run build`로 `dist/`를 먼저 만들어야 한다. (sealed-env-studio 주석: "evaluates `frontendDist` at compile time and panics if the path doesn't exist. We need a real dist/ before cargo touches the lib crate (clippy, test).")
2. **표준 Rust 잡**: `dtolnay/rust-toolchain@stable`(components: rustfmt, clippy) → `Swatinem/rust-cache@v2` → `cargo fmt --manifest-path src-tauri/Cargo.toml -- --check` → `cargo clippy --all-targets -- -D warnings` → `cargo test`. mimi는 `cargo fmt`→`clippy`→`test` 순서 그대로.
3. **프론트엔드 잡(병렬)**: `actions/setup-node` → `npm ci` → typecheck(`tsc --noEmit` 또는 `tsc -b`) → lint → frontend test(vitest) → `npm run build`(스모크).
4. **빌드 잡(needs: 품질 잡들)**: tauri-action 또는 `npm run tauri build -- --debug`(서명 없이 컴파일 스모크) — "각 OS에서 컴파일되는가"를 게이트. 릴리스는 별도.
5. **권장 구석메모 게이트(제안)**:
   ```
   job: quality (ubuntu + windows 매트릭스 또는 windows 단일)
     - npm ci → npm run build  (dist 생성: generate_context! 전제)
     - cargo fmt -- --check
     - cargo clippy --all-targets -- -D warnings
     - cargo test (순수 로직 + tauri::test)
   job: smoke (windows-latest)
     - WebView2 evergreen bootstrapper로 런타임 보장
     - tauri build (debug) → app.exe 생성
     - app.exe --selftest → guseok-qa.log artifact 업로드, 종료코드로 게이트
   선택 job: e2e (windows-latest)
     - @wdio/tauri-service (embedded 또는 external+autoDownloadEdgeDriver)
       또는 plan_setup CDP 스크립트를 CI 스텝으로 실행
   ```
6. **lint 잡 분리 이유**: clippy는 빌드보다 훨씬 빠르므로, 빌드 실패 전에 lint/포맷에서 먼저 끊는 게 비용 효율적 — 공식 CI 예시도 cargo test를 e2e 전에 둔다.

### E. store.json 마이그레이션 회귀 테스트 패턴

**E-1. 플러그인 현실**
- `tauri-plugin-store`는 단일 JSON 파일이며 **마이그레이션 프레임워크 없음**(codegiz: "has no migration framework — it's a plain JSON file").
- `defaults`/`StoreBuilder::default`는 "최초 생성 시에만" 시드 — 이후 실행에서 기존 파일에 새 키가 자동으로 생기지 않는다. 스키마 진화는 코드로 처리해야 함.
- `overrideDefaults`/`createNew` 같은 옵션은 덮어쓰기용이지 마이그레이션 도구가 아님.

**E-2. 사실상 표준 패턴 — `__version` 키 + 로드 시 마이그레이션**
- codegiz 권장: store 로드 직후 `__version` 읽고 `if (version < N) { 단계별 변환; __version = N }` 체인. 명시적·프레임워크 없이 동작.
- 마이그레이션은 "한 단계씩 연쇄"(v0→v1→v2…)로 구현해 어떤 구버전에서 와도 최신이 되게 한다.

**E-3. 회귀 테스트 3층 구조(권장)**
- **층1 — 순수 함수 단위 테스트(가장 가성비)**: 마이그레이션 로직을 `migrateStore(json: object): object` 같은 순수 함수로 분리하고, repo에 `fixtures/store-v0.json`, `store-v1.json` 등 구버전 스냅샷을 커밋. 각 fixture에 대해 migrate 결과가 최신 스키마와 일치하는지 단언. JS 측이면 vitest(프레임 불필요), Rust 측이면 `serde_json::Value` 단위 테스트. tauri-cli 자체 마이그레이션도 fixture 파일 + 테스트 방식(`can_migrate_api_example_config` 등).
- **층2 — 로드 경로 통합 테스트**: mockIPC로 store invoke를 모킹하거나, vitest에서 실제 `migrate` 호출을 감싼 테스트로 "로드 → 구버전 감지 → 변환 → 저장" 흐름을 검증.
- **층3 — 앱 레벨 회귀(기존 하네스 활용)**: 테스트 시작 전 `%APPDATA%/<identifier>/store.json`에 구버전 fixture를 심고 → `--selftest` 기동 → 마이그레이션 후 읽은 값/버전이 기대치인지 로그로 검증. store 경로는 `BaseDirectory::AppData` 기준으로 resolve되므로 경로 결정론적. 이게 "실제 사용자 업그레이드" 시나리오를 가장 잘 재현.
- 주의: store는 공유 리소스(Rust `StoreExt`와 JS `load`가 같은 파일)라 어느 쪽에서 마이그레이션을 수행할지를 한 곳으로 정해야 이중 실행 레이스를 피한다.

**E-4. 구석메모에의 적용 힌트**
- 현재 selftest 26개에 "구버전 store.json → 마이그레이션 검증" 케이스를 추가하는 것이 가장 적은 비용. selftest가 임시 user-data/profile을 쓰도록 격리하면 실제 사용자 데이터 오염 없이 CI에서도 실행 가능(WEBVIEW2_USER_DATA_FOLDER 또는 앱 데이터 경로 오버라이드).
