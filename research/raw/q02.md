## 1. WebView2 멀티윈도우 / 투명 창의 알려진 이슈

### 1.1 투명 창 필수 조합 (handles 창에 직접 해당)

- **함정**: v2에서는 `window-shadows`가 코어에 통합되어 **기본 활성화**다. `transparent:true` + `decorations:false`만으로는 불투명 배경이 남는다. `shadow:false`까지 명시해야 한다(issue #8308/#8133 계열, #15947에서도 `shadow:false` 조합으로 보고됨).
- **권장 패턴**: handles 창 설정 = `transparent:true, decorations:false, shadow:false, alwaysOnTop:true, skipTaskbar:true`. 또한 `html/body` 배경도 투명해야 한다(CSS `#11551` 계열 — 윈도우 플래그만으로는 부족).
- **생성 시 흰 플래시**: 투명 창 생성 직후 webview 렌더 전에 흰 redirection bitmap 프레임이 보이는 문제 → **tauri 2.12.0의 `noRedirectionBitmap`**(WS_EX_NOREDIRECTIONBITMAP, DirectComposition 경로)로 회피 가능. PR #15410이 2026-07-03 머지, 2.12.0(2026-09-26)에 포함. 설정 키 `app > windows > noRedirectionBitmap`, JS `WebviewWindow` 생성자 옵션 `noRedirectionBitmap`도 존재.
- **DWM 합성 경쟁(Windows 10)**: 투명+alwaysOnTop 창에서 `set_ignore_cursor_events`를 자주 토글하거나 최소화/복원할 때 투명 영역·바탕화면이 간헐적으로 검게 렌더링된다(issue #15947, 미해결 2026-08-30 등록). 원인 가설: tao가 투명 창에 쓰는 `DwmEnableBlurBehindWindow` + 빈 region 해킹과 `WS_EX_LAYERED` 토글이 DWM 합성 트리 재구성과 경합. **완화 패턴**: ① `noRedirectionBitmap`으로 BlurBehind 경로 자체를 우회, ② 최소화 대신 hide(또는 트레이), ③ 커서 이벤트 토글 디바운스. 구석메모의 handles(40px 투명 AOT)가 바로 이 형태라 Win10 사용자 대상으로 재현 테스트 권장.
- **런타임 회귀 위험**: WebView2 Evergreen 런타임 업데이트가 투명 렌더링을 깨뜨린 사례가 반복 보고됨(144.x 투명 창 아티팩트→144.0.3719.93 핫픽스; 154에서 alpha=0 무시하고 테마색 배경 칠하는 회귀, WebView2Feedback #5492/#5752 — 검색 결과로만 확인, 확신도 중간). **사용자 리포트에 "WebView2 런타임 버전"을 항상 수집**하고 Beta/Dev 채널로 선행 테스트.

### 1.2 멀티윈도우 + IME(한국어 직접 해당 — panel/settings 창)

- **창 전환 시 IME 조합창 이탈**: 같은 프로세스의 두 top-level 창이 **하나의 user data folder(=하나의 브라우저 프로세스)를 공유**할 때, 창 A↔B를 번갈아 클릭하며 CJK IME로 입력하면 한쪽 창에서 조합창(`MSCTFIME Composition`, 후보창)이 화면 좌상단 (0,0)에 뜨고 `compositionstart`가 페이지에 도달하지 않는다. 20회 중 10회 재현(WebView2Feedback #5799, Runtime 157.0.4341.42에서도 재현 — 매우 최신 문제). 원인: `WM_SETFOCUS` 처리 중 활성화가 끝나기 전에 `MoveFocus(PROGRAMMATIC)`를 동기 호출하면 TSF 포커스가 잘못된 document manager에 연결됨. Microsoft 자체 WinForms WebView2에서도 재현 → **근본 원인은 WebView2 쪽**.
  - wry 완화 PR #1924(메시지를 post해서 활성화 완료 후 `MoveFocus`, 단 `GetFocus()==hwnd`일 때만): 10/20 실패 → 약 2/280. **아직 미머지(open)** — tauri/wry 버전업 시 이 PR 포함 여부 확인 필요.
  - 회피책: 창별 UDF 분리는 0/20이나 Tauri에서 창별 UDF 분리는 사실상 불가 → 업스트림 수정 대기 + 한글 IME 재현 테스트 체크리스트화.
- **기존 텍스트가 있는 입력창 첫 포커스 시 TSF 동결**(tauri #15436, 미해결): 내용이 채워진 `<textarea>`/contenteditable을 처음 포커스하면 TSF 초기화와 TextInputStateChanged 동기화 이벤트가 엇갈려 HIMC 상태가 오염, CJK IME 조합창이 안 뜨고 키 입력이 삼켜진다. 빈 입력창은 정상. **메모 앱은 "기존 메모를 로드한 textarea"가 정확히 이 조건**이라 재현 가능성이 가장 높은 이슈.
  - 부분적 우회: 렌더 후 빈 `<textarea>`를 프로그램적으로 focus()→blur()해 TSF를 미리 초기화(단, 사용자 첫 클릭이 그 요소면 재발). ImmAssociateContext 계열 Win32 접근·JS 더미 입력·값 비우기 등은 모두 무효로 보고됨.
- **창 리사이즈 후 조합창이 좌상단으로**(WebView2Feedback #5675, 검색 결과 요약): 한국어 IME로 리사이즈 직후 입력하면 조합창이 캐럿 대신 좌상단에 표시. 커밋된 텍스트는 정상 입력. 창 이동/재포커스로 회복.
- **contentEditable CJK 버그**(WebView2Feedback #5625): contentEditable에서 첫 글자 유실·전각 문장부호 두 번 입력 필요(서드파티 IME에서 심각, 렌더러 메인 스레드가 바쁘면 MS IME도 재발). 같은 페이지 `<textarea>`는 정상. JS 레이어 완화 불가. **권장: 메모 본문은 contentEditable 리치 에디터 대신 `<textarea>` 유지** — 구석메모의 Vanilla JS textarea 설계가 오히려 안전한 선택.
- **포커스 미전달**: Windows에서 alt-tab/작업표시줄 클릭으로 top-level 창이 포커스돼도 WebView2 자식이 키보드 포커스를 받지 못하는 경우가 있다(실전 앱 사례). 패턴: `WindowEvent::Focused(true)`에서 `getCurrentWebview().setFocus()`(=`controller.MoveFocus`) 호출. 단, 위 IME 버그와 상호작용 가능 — wry #1924 머지 후 조합해서 검증.
- **동기 컨텍스트에서 창/webview 생성 데드락**: `Window::builder`, `Window::add_child`(multiwebview)를 Windows에서 **동기 커맨드·이벤트 핸들러 안에서 호출하면 데드락**(docs.rs 공식 Known issues). → `async` 커맨드 + 별도 스레드. 구석메모는 `app.windows`가 빈 배열이고 모든 창을 런타임 생성하므로 `WebviewWindowBuilder` 호출 위치를 반드시 async 컨텍스트로.
- **alwaysOnTop과 작업표시줄**: Win11에서 Win 키/작업표시줄 클릭 시 AOT 창이 작업표시줄 뒤로 가는 보고(#9987 스레드). 근본 해결 API는 없음.
- **HTML5 DnD**: Windows에서 Tauri가 WebView2의 드래그앤드롭 핸들러를 교체하므로 DOM `dragstart/drop`이 동작하지 않는다. 프론트에서 HTML5 DnD가 필요하면 `dragDropEnabled:false`(파일 드롭 `tauri://drag-drop` 이벤트와 상호 배타).

## 2. tauri-plugin-updater 운영상 주의점

### 2.1 서명·키 관리

- **서명은 필수, 비활성화 불가**. 공개키는 `tauri.conf.json`의 `plugins.updater.pubkey`에 **내용 자체**로(파일 경로 불가). 구석메모는 이미 설정됨.
- **개인키 분실 = 설치 기반 전체에 업데이트 불가**(공식 문서가 강조). 새 키페어로 만든 업데이트는 기존 바이너리의 공개키와 불일치 → 유일한 복구는 수동 재설치. 비밀번호 매니저/시크릿 볼트에 보관하고 GitHub Secrets만을 유일 백업으로 두지 말 것(읽기 불가).
- 빌드 시 `TAURI_SIGNING_PRIVATE_KEY` + 선택적으로 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 환경변수. **`.env` 파일은 인식되지 않음**. PowerShell: `$env:TAURI_SIGNING_PRIVATE_KEY="..."`.
- Windows에서 updater 키와 별개로 **Authenticode 코드서명**(SmartScreen)이 있음 — 서명되지 않은 NSIS 설치/업데이트는 SmartScreen 경고를 유발.
- updater 2.13.3: `minisign-verify` 0.3으로 비정규 Ed25519 S값 서명 거부 — 최신 플러그인이 더 엄격.

### 2.2 아티팩트·릴리스 절차

- `bundle.createUpdaterArtifacts`: v2 네이티브는 `true`(현재 구석메모 설정 그대로 정답). `"v1Compatible"`은 v1 배포 사용자가 있는 앱 전용이며 **v3에서 제거 예정**. v1Compatible 모드는 Windows에서 `.nsis.zip` 업데이트 번들을 만들고, `true` 모드는 `*-setup.exe` 자체가 업데이트 번들.
- 정적 JSON(`latest.json`) 경로 사용 중: `version`, `platforms.<OS-ARCH>.url`, `platforms.<OS-ARCH>.signature` 필수. **signature는 .sig 파일 내용**(경로/URL 아님). Tauri는 버전 비교 전에 JSON 전체를 검증 → 플랫폼 항목 하나라도 불완전하면 업데이트 실패. Windows-only 앱이면 `windows-x86_64`만 있어도 되지만, 쓰는 항목은 완전해야 함.
- `endpoints`는 앞 URL이 **non-2XX**일 때만 다음으로 진행 — 200인데 잘못된 JSON이면 failover 안 됨. TLS 강제, `dangerousInsecureTransportProtocol` 비권장(2.14.0부터 http URL 시 경고 로그).
- tauri-action은 `.sig`들로 `latest.json`을 자동 생성해 GitHub Releases에 업로드(`uploadUpdaterJson`). 릴리스는 **draft로 만들고 모든 빌드 완료 후 publish** 권장 — latest.json이 먼저 공개되면 아티팩트 미업로드 상태에서 업데이트 실패 가능.
- **버전 0.x 주의**: SemVer 비교 기준 현재 버전보다 새 버전만 업데이트로 인정.

### 2.3 Windows 설치 모드·롤백

- `windows.installMode`: `passive`(기본, 진행바만, 무인터랙션, 권장 — 현재 설정), `basicUi`(사용자 상호작용 필요), `quiet`(권한상승 불가, perMachine엔 부적합, 비권장). 구석메모는 NSIS `installMode: currentUser` + updater `passive` 조합으로 권한상승 없이 업데이트 가능한 모범 구성.
- 과거 Windows 업데이터 함정(현재 해결됨, 구버전 사용자 주의): NSIS perMachine/both 설치 시 비관리자 업데이트 실패(#7184→수정), 다중 사용자 환경에서 프로세스명만으로 실행중 판별해 실패(#8223→upstream 수정), PowerShell 경유 실행 PermissionDenied(#9737→ShellExecute로 이전). updater 2.14.0부터 ShellExecuteW 실패 원인(예: UAC 거부 시 "Access is denied")을 정확히 보고.
- **롤백(다운그레이드)**: updater 2.12.0부터 `allowDowngrades`가 JS `check()` 옵션에서 **플러그인 설정으로 이동(브레이킹)** — 웹뷰 임의 코드가 버전 체크를 완화할 수 없게 하는 보안 변경. 기본 false. 정적 latest.json으로 "이전 버전 배포"하려면 `"plugins": {"updater": {"allowDowngrades": true}}` 필요. 또는 동적 서버 + Rust `default_version_comparator` 커스터마이즈로 서버 지시 버전을 설치(공식 문서가 롤백 용도로 안내).
  - 추가로 "다운로드는 했지만 설치 전 앱이 꺼진" 경우 대비 `Updater::restore_update`(캐시된 메타데이터 복원)와 `Update::verify`(바이트 검증)가 2.14.0에 추가. `install`은 이제 설치 전 패키지 바이트를 검증.
- `restartAfterInstall`(2.11.0): 설치 후 인스톨러가 앱을 재실행하지 않게 하는 옵션 — 트레이 상주 앱에서 업데이트 후 제어된 재시작을 원할 때 유용.
- `Update.download()` 재호출 시 이전 다운로드 바이트 해제(2.14.0) — 구버전은 webview 생명주기까지 메모리 유지.

  - JS `exit()` API + `core:app:allow-exit`(2.12.0) — plugin-process 없이 종료 가능.
  - `Window::set_fullscreen_on_monitor`(2.12.0).

## 4. 단일 파일 JSON 저장 vs SQLite 등 저장 방식

### 4.1 선택 기준(공식/실무 공통 가이드)

| 데이터 종류 | 권장 | 이유 |
|---|---|---|
| 설정·테마·창 상태·마지막 경로 | `tauri-plugin-store`(JSON) 또는 자체 JSON | 키 소수, 쿼리 불필요 |
| 메모 레코드 다수·검색·필터·페이징 | `tauri-plugin-sql`(sqlite 피처) | 인덱스·쿼리·부분 갱신·마이그레이션 |
| 토큰·비밀번호 | stronghold/OS 키체인 | store/SQLite는 평문 |
| 일시 캐시 | 메모리 `State` | 영속 불필요 |

- 경험칙: **JSON 한 파일 ≲1MB, 키 수십 개**면 store/자체 JSON이 정답. "테마 기억하려고 SQLite"는 과잉.
- 파일 분리: 관심사별 파일을 나누면 손상 격리에 유리(settings.json / window-state.json / auth-cache.json 등).

### 4.2 구석메모(자체 JSON + 원자적 교체) 관점의 함정

- **원자적 교체는 "손상 방지"이지 "동시성 제어"가 아니다**: 같은 경로에 여러 라이터가 동시에 쓰면 **last-writer-wins**(safe-write 문서 명시). 패널 창 여러 개가 각자 메모를 편집하며 **하나의 JSON 파일 전체를 통째로 교체**하는 구조라면, 창 A의 저장이 창 B의 직전 저장을 덮어쓸 수 있다 → 멀티윈도우에서는 ① 창별 파일 분리, ② Rust 측 단일 라이터(모든 저장을 한 커맨드로 직렬화하고 read-modify-write를 Rust에서 수행), ③ SQLite 이전 중 선택 필요.
- **Windows 특유의 rename 실패**: 대상 파일을 다른 프로세스(백신·인덱서·동기화 클라이언트)가 열고 있으면 교체가 대기 없이 실패 → **짧은 재시도** 필요(safe-write가 이를 구현). 또한 Windows는 디렉터리를 파일로 열 수 없어 rename 내구성 fsync를 건너뜀(정전 대비 한계).
- 임시파일은 **반드시 대상과 같은 디렉터리**에(크로스 볼륨 rename은 비원자적 복사로 퇴보).
- 백업본 유지 권장: 저장 전 `memos.json.bak`을 만들어 두면 논리적 손상(정상 JSON인데 내용 유실)에서 복구 가능 — 원자적 교체는 바이트 손상만 막는다.
- `tauri-plugin-store` 참고: `autoSave`는 기본 100ms 디바운스, 꺼두면 `save()` 누락이 "저장 안 됨"의 최다 원인. JS 값은 `serde_json::Value` 호환이어야 함. 파일은 앱 데이터 디렉터리(`%APPDATA%/<identifier>`).
- `window-state` 플러그인은 `.window-state.json`을 `std::fs::write`로 **비원자적** 기록하고, 복원 시 `available_monitors()`로 저장된 모니터 존재 여부를 검증한다 — 구석메모의 자체 원자적 JSON + `MonitorFromPoint` 검증 방식이 동등 이상이며, 멀티모니터 "마지막 모니터 기억"은 플러그인도 미해결(plugins-workspace #1282, 미해결).

### 4.3 SQLite로 옮길 때의 함정

- `Cargo.toml`에 `features=["sqlite"]` 없으면 컴파일 불가.
- **마이그레이션 불변성**: 실행된 `version`의 SQL을 수정해도 이미 설치된 앱엔 적용 안 됨 → 항상 새 version 추가.
- 쿼리는 반드시 파라미터 바인딩(문자열 연결 → 인젝션).
- 비용: 의존성·마이그레이션 관리·런타임 복잡도 증가. 메모 수백~수천 건 + 검색/부분업데이트가 필요해질 때가 전환 시점.

## 5. WebView2 앱의 메모리/성능 최적화

### 5.1 프로세스 모델 이해

- WebView2는 컨트롤마다 브라우저/렌더러/GPU 등 프로세스 묶음을 만든다. **같은 Environment+UDF를 공유하면 프로세스가 공유**돼 메모리가 절감된다 — Tauri는 앱 내 모든 창이 기본적으로 같은 WebContext/UDF를 공유(메모리엔 유리, §1.2의 IME 버그 원인이기도 함).
- 창을 모두 닫아도 WebView2 프로세스가 즉시 죽지는 않으나 **약 15초 내 종료**되는 것이 정상(#16528, 제보자 측정 오류로 종결 — "프로세스가 영구 상주한다"는 비판은 오해).
- 트레이 상주 앱의 실전 패턴: 창을 `hide()` 대신 **destroy하고 트레이에서 재생성**하면 idle 메모리가 크게 줄고(사례: 웹뷰 제거 후 ~113MB private 절감 시도), 제거 후 `EmptyWorkingSet`/`SetProcessWorkingSetSize`(Windows), `malloc_trim`(Linux) 같은 OS 수준 트리밍 요청을 병행(서드파티 PR 사례 — best-effort).
- `WebviewWindow`/`Window` 생성 자체가 무겁다(콜드 스타트 지연). 숨김↔재생성 빈도와 체감 속도를 트레이드오프로 결정 — 구석메모의 panel/settings는 hide/show 재사용이, 장기 미사용 handles라면 destroy 고려.

### 5.2 메모리 관리 API

- **비활성 webview에 `MemoryUsageTargetLevel=Low`** — 브라우저 엔진이 캐시 데이터 드롭/디스크 스왑을 유도. 활성화 시 `Normal`로 복원. wry는 `WebViewExtWindows::set_memory_usage_level`(ICoreWebView2_19 매핑)로 노출 — **창이 숨겨진 동안 Low로 설정하는 패턴 권장**.
- 장기 미사용 인스턴스는 `TrySuspendAsync()`로 렌더러 일시중지(스크립트 정지) → `Resume()`으로 복귀(best-effort).
- 불필요한 WebView2 인스턴스 생성 금지: 페이지 전환은 재생성보다 navigate 재사용.
- UDF(유저 데이터 폴더)는 기본 로컬 앱데이터에 유지 — 느린 드라이브/네트워크 공유 금지.
- 호스트 측 메모리: 큰 객체 그래프를 AddHostObjectToScript로 노출하지 말 것(GC 방지), 사용 끝나면 RemoveHostObjectFromScript, 이벤트 핸들러 해제 후 Dispose.

### 5.3 CPU·렌더링·IPC

- **GPU 가속 끄지 말 것**(`disable-gpu`는 트러블슈팅용) — WebView2는 기본 GPU 렌더링.
- 웹 콘텐츠: 무거운 JS 제한, 디바운스/스로틀, 애니메이션은 CSS, layout thrashing 회피, 초기 페이로드를 정적 HTML 위주로(구석메모의 Vanilla JS는 이미 유리), 지연 로딩.
- **IPC 배치**: web↔host 잦은 호출은 CPU를 올린다 — 메시지를 묶고, 빈번한 통신엔 host object보다 web message가 단순·빠름(Tauri invoke도 결국 IPC — 초당 수십 회 폴링 패턴은 이벤트 푸시로 전환 검토).
- 호스트의 무거운 네이티브 작업이 WebView2 스레드를 굶기지 않게 스레드 우선순위 관리.
- 무거운 네이티브 작업은 Rust 비동기(도쿄)로 오프로드 — JS 이벤트 루프가 아니라 webview 렌더러의 메인 스레드 busy가 IME 유실(§1.2)을 악화시키므로 **렌더러 메인 스레드를 비우는 것이 한국어 입력 품질에도 직결**.

### 5.4 런타임·관측

- Evergreen 런타임 권장(자동 성능/보안 개선)하되, **Beta/Dev/Canary 프리뷰 채널로 선행 테스트** — 투명 창 회귀(§1.1)처럼 앱이 먼저 깨지는 사례가 있음. Edge가 켜져 있고 버전이 같으면 바이너리가 이미 메모리에 있어 시작이 빠름.
- 트러블슈팅 도구: `WebView2.wprp` ETW 트레이스(WPR/WPA), `edge://inspect`, DevTools Memory/Performance, Browser Task Manager. 최소 HTML로 재현 → 콘텐츠 문제 vs 런타임/호스트 문제를 분리하는 것이 공식 절차.

2. `rust-version`을 1.90으로 갱신(실제 요구와 표기 일치).
3. 한국어 IME 시나리오 테스트: "기존 메모가 있는 textarea 첫 포커스" (#15436), "handles↔panel 전환 후 한글 입력"(#5799) 재현 체크리스트. 리치 에디터 도입 계획이 있다면 Windows에서는 textarea 유지 권장.
4. 저장 파이프라인: 단일 JSON + 멀티 패널 동시 편집이면 last-writer-wins 유실 경로 점검 → Rust 단일 라이터 직렬화 또는 창별 파일/ SQLite 전환 판단. rename 실패 재시도 + `.bak` 유지.
5. updater: `allowDowngrades`(2.12.0+) 설정으로 핫픽스 롤백 경로 확보 여부 결정. 릴리스는 draft → 아티팩트+latest.json 완비 후 publish 순서.
6. 트레이 상주 시 panel/settings 숨김 중 `set_memory_usage_level(Low)` 적용(wry `WebViewExtWindows`), 필요 시 destroy-재생성 패턴 검토.
7. 창/webview 런타임 생성은 모두 async 커맨드/스레드에서(동기 호출 데드락, 공식 문서).
